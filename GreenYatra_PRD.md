---

## 1. Executive Summary

GreenYatra is a two-sided platform that closes the loop between traveler behavior and hotel sustainability. Hotels use a B2B dashboard to identify and act on resource-efficiency opportunities, earning a dynamic **Green Score** and tag. Travelers use a B2C app to plan lower-carbon, accessibility-aware trips and discover hotels ranked by that same Green Score. During their stay, guests can opt into a gamified loyalty program that rewards low-resource-usage behavior with hotel-funded perks. The savings generated by that behavior feed back into the hotel's Green Score, reinforcing the cycle.

The platform's core differentiator is that **the Green Score is a single, shared, live metric** — not three separate scoring systems — computed from real resource data and behavioral signals rather than a static, self-declared "eco-friendly" badge.

---

## 2. Problem Statement

Travelers must currently choose between cost, convenience, and environmental impact without clear information, and have no easy way to filter for accessibility needs. Hospitality businesses lack intelligent tools to identify where they're wasting energy, water, and food, and have no market incentive to fix it because "sustainability" is not visibly rewarded in traveler-facing search and booking. GreenYatra addresses both sides simultaneously by making sustainability a mutually reinforcing incentive rather than a one-directional certification.

## 4. Users & Personas

**Traveler ("Eco-conscious explorer")** — Planning a trip, cares about cost/time but wants visibility into environmental impact; may have accessibility requirements (mobility, visual, hearing).

**Hotel Manager ("Sustainability-motivated operator")** — Wants to reduce operating costs (energy, water, food waste) and attract more bookings; needs clear, prioritized, low-effort actions rather than vague sustainability advice.

**Hotel Guest (in-stay)** — Same person as the Traveler persona, now checked in; motivated by small, immediate rewards (drinks, late checkout) more than abstract environmental impact.

## 6. Feature Requirements

### 6.1 B2C — Green & Accessible Trip Planner

**Description:** Traveler enters an origin and destination as **free text at any granularity** — a city, a neighborhood, a landmark, an address, a small town — not a fixed dropdown of pre-seeded city pairs. The system dynamically resolves both locations, reasons about which transport modes are actually viable between them, fetches real emissions/distance/cost data for each viable mode, and returns a ranked, explained comparison. Nothing about the transport comparison is hardcoded or pre-programmed per route.

**How real-time resolution works (no fixed city list):**
1. **Geocoding:** Both free-text inputs are resolved via Mapbox Geocoding API into coordinates + place metadata (place type, city, region, country). Works for any place Mapbox can geocode, not a seed list.
2. **Mode feasibility reasoning (Gemini):** Given the two geocoded locations, Gemini determines which transport modes are realistically viable for that specific pair (e.g., flight is only offered if both locations are reasonably near an airport and the distance justifies it; train only if a rail connection is plausible for that region; shared EV/cab only within a sensible driving range) and identifies the nearest relevant anchor points for each mode (nearest airport(s), nearest major train stations). This replaces any hardcoded city↔airport table — it works for arbitrary inputs because Gemini reasons over the geocoded context rather than a lookup table.
3. **Real distance/duration:** Mapbox Directions API computes actual driving distance/duration between the resolved points (or between the resolved point and the nearest relevant station/airport, for mixed-mode legs like "drive to the airport, then fly").
4. **Real emissions:** Climatiq API computes CO2e for every viable mode — flight, train, bus, car, shared EV — using the real distance from step 3 (and airport-pair/cabin-class inputs where Climatiq's flight activity factors call for them). Climatiq is the single emissions source across all modes, so there's one consistent calculation path rather than mixing providers.
5. **Explanation (Gemini):** Once all real numbers are assembled, Gemini generates the plain-language "why" and the relatable carbon-impact translation. Gemini is used here for language generation only — it does not invent the numbers themselves.
6. **Caching:** Geocoding results, mode-feasibility reasoning, and computed route/emissions data are cached in Upstash Redis (see Section 7) keyed by normalized location pair + mode, so repeated or similar queries during a session/demo are fast and don't re-spend API calls.

**Requirements:**
- FR1.1: User can input origin and destination as free text (any place granularity), plus travel dates.
- FR1.2: User can optionally toggle accessibility filters: step-free access, wheelchair accessible, visual assistance, hearing assistance.
- FR1.3: System dynamically determines viable transport modes for the specific input pair (not a fixed mode list) and returns each with: duration, cost (where obtainable), CO2e (kg), and a relatable carbon-impact translation.
- FR1.4: System explains, in plain language (via Gemini), why the top-ranked option is recommended, using the actual computed numbers.
- FR1.5: Map view (Mapbox) shows the resolved route(s) visually for any input pair.
- FR1.6: For multi-stop trips, Gemini reasons over the full set of resolved locations to suggest sequencing/mode choices that reduce total footprint (e.g., recommending a train hop between two nearby resolved points instead of two separate flights). This is genuine reasoning over the specific inputs, not a pre-set rule for known city pairs.
- FR1.7: Hotel results near the resolved destination are filtered by any active accessibility toggle and sorted by Green Score by default (with option to re-sort by price/rating).
- FR1.8: If Gemini determines a mode is not realistically viable for a given pair (e.g., no sensible flight option for two adjacent towns), that mode is simply omitted rather than shown with fabricated numbers.

**Acceptance Criteria:** Given two arbitrary, previously-unseen free-text locations (not present in any seed list), the planner completes geocoding → mode reasoning → real distance/emissions lookups via Climatiq → ranked results end-to-end, without any hardcoded per-route data. A repeat query for the same pair returns from Redis cache in under ~300ms instead of re-calling external APIs.

### 6.2 B2C — Green Score Hotel Discovery

**Description:** Hotels are browsable/searchable with a visible Green Score (0–100) and tag (None/Bronze/Silver/Gold), sourced live from the B2B module.

**Requirements:**
- FR2.1: Hotel list/detail view displays Green Score, tag, and a breakdown (energy, water, food/waste, guest behavior, accessibility baseline).
- FR2.2: Score breakdown is expandable — user can see *why* a hotel has its score, not just the number (anti-greenwashing requirement).
- FR2.3: Hotel detail page lists verified sustainability actions the hotel has completed.

**Acceptance Criteria:** Clicking into any seeded hotel shows a score breakdown that sums correctly to the displayed total score using the formula in Section 8.

---

### 6.3 B2C — In-Stay Gamification (Eco-Points)

**Description:** After check-in, the guest's app view switches to "Stay Mode," offering opt-in green actions for points, redeemable at the hotel.

**Requirements:**
- FR3.1: Guest can opt in at check-in (simulated check-in flow, no real PMS integration).
- FR3.2: App presents daily nudges/toggles: e.g., "Skip housekeeping today," "Keep AC at 24°C," "Reuse towels."
- FR3.3: Each action awards a fixed point value (configurable per hotel).
- FR3.4: Points accumulate visibly; guest can redeem for hotel-defined rewards (free cocktail, dessert, late checkout) via a redemption code shown to staff.
- FR3.5: Actions logged here feed into the hotel's Guest Behavior Score (Section 8).

**Acceptance Criteria:** A simulated guest completing 3 actions across a 2-night stay accumulates points correctly and can generate a redemption code.

---

### 6.4 B2B — Hotel Onboarding & Baseline Audit

**Description:** New hotels complete a structured self-assessment establishing their starting Green Score.

**Requirements:**
- FR4.1: Onboarding form covers: energy (renewable %, HVAC efficiency, lighting type), water (greywater recycling, low-flow fixtures), food (local sourcing %, buffet-vs-order ratio, waste tracking), waste (recycling program, single-use plastic elimination), and a light accessibility checklist (step-free access, accessible room count, staff training).
- FR4.2: On submission, system computes an initial Baseline Score and assigns starting tier (minimum: no tag until audit is complete; audit alone can reach Bronze).

**Acceptance Criteria:** Submitting the audit form produces a non-zero baseline score visible immediately on the hotel dashboard.

---

### 6.5 B2B — Resource Usage Dashboard

**Description:** Hotel manager views time-series charts of simulated energy, water, and food-waste data, with peer benchmarking.

**Requirements:**
- FR5.1: Dashboard displays 90-day (or configurable range) charts for energy (kWh), water (liters), and food waste (kg), sourced from simulated seed data.
- FR5.2: Dashboard shows a peer benchmark line (average of similarly-sized/rated hotels) for comparison.
- FR5.3: System flags anomalies (usage significantly above benchmark or historical pattern).

**Acceptance Criteria:** At least one seeded hotel shows a visible, clearly flagged anomaly in the demo dataset.

---

### 6.6 B2B — AI Recommendation Engine (Gemini, Tier 2)

**Description:** On demand (or scheduled), the system sends recent usage + benchmark data to Gemini 3.6-Flash, which identifies inefficiencies and returns structured, actionable recommendations with estimated impact.

**Requirements:**
- FR6.1: Manager can trigger "Generate Recommendations" from the dashboard.
- FR6.2: System sends structured usage/benchmark JSON to Gemini with a prompt requiring strict JSON-only output (category, recommendation text, estimated impact).
- FR6.3: Recommendations are stored with a status: Suggested → In Progress → Verified Complete, manually updatable by the hotel manager.
- FR6.4: Verified Complete recommendations contribute to the Recommendation Completion Rate sub-score (Section 8).

**Acceptance Criteria:** Triggering generation for a seeded hotel returns 1–3 valid, parseable recommendations tied to actual anomalies in that hotel's data.

---

### 6.7 B2B — Live Green Score & Tag

**Description:** The hotel's Green Score recomputes based on the formula in Section 8 and updates the dashboard and B2C-facing tag in near-real-time (on data change or manual refresh).

**Requirements:**
- FR7.1: Dashboard displays current score, tier, and a one-line "compared to last period" delta.
- FR7.2: Dashboard shows the estimated effect of the score on visibility (e.g., "You are appearing in X% more traveler searches").

**Acceptance Criteria:** Marking a recommendation as "Verified Complete" visibly increases the hotel's Green Score on next reload.

---

### 6.8 B2B — ROI Tracker

**Description:** Shows the hotel manager the net financial impact of the loyalty program, to justify the cost of guest rewards.

**Requirements:**
- FR8.1: Dashboard computes: estimated savings from guest eco-actions (labor/utilities) minus cost of rewards redeemed, over a selectable period.
- FR8.2: Displays participation rate (% of guests opted in) and average savings/redemption cost per opted-in guest, for transparency.

**Acceptance Criteria:** ROI Tracker shows a positive net figure for at least one seeded hotel with simulated stay data, with the underlying assumptions visible.

## 7. Technical Architecture

**Stack:**
- **Frontend/Backend:** Next.js (App Router) — single app, route groups `/traveler/*` and `/hotel/*`, API routes for backend logic
- **Database/Auth:** Supabase (Postgres, Auth with role-based `user_metadata`, Realtime for score updates)
- **Cache/Fast Store:** Upstash Redis — geocoding cache, mode-feasibility/reasoning cache, route+emissions cache, and (optional) fast in-stay point counters
- **LLM:** Gemini 3.6-Flash — used specifically for: (a) B2B recommendation generation, (b) trip-mode feasibility reasoning for arbitrary location pairs, (c) plain-language explanations of scores/recommendations/route choices, (d) multi-stop sequencing suggestions. Gemini is never used to invent numeric data (distance, cost, CO2e) — those always come from Climatiq or Mapbox.
- **Carbon data:** Climatiq API — single source for emissions across all transport modes (flight, train, bus, car, shared EV)
- **Mapping/Distance:** Mapbox (geocoding, directions, route visualization)

**Architecture diagram:**
```
Next.js App (traveler + hotel routes)
        │
        ▼
   API Route Handlers
        │
        ├── Upstash Redis (cache-first layer: geocoding, mode reasoning, route/emissions)
        ├── Supabase (Postgres/Auth/Realtime — hotels, usage, recos, stays)
        ├── Gemini 3.6-Flash (mode reasoning, recommendations, explanations, sequencing)
        ├── Climatiq API (emissions for all transport modes, incl. flights)
        └── Mapbox (geocoding, directions, maps)
```

**Reliability pattern:** All external calls (Mapbox geocoding/directions, Climatiq, and Gemini mode-feasibility reasoning) go through a cache-first wrapper backed by Upstash Redis:
- Geocoding results: long TTL (e.g., 30 days) — a place's coordinates rarely change.
- Mode-feasibility reasoning: medium TTL (e.g., 7 days) — viable modes for a location pair are stable.
- Route/emissions numbers: short TTL (e.g., 24 hours) — allows for pricing/schedule drift without constant re-fetching.

This protects the live demo from API downtime/rate limits without relying on hardcoded per-route data — the *first* time a novel pair is queried it's fully live and dynamic; every repeat is fast and cheap. Common demo routes can still be pre-warmed before presentation for extra safety.

## 8. Green Score Formula

```
Green Score (0–100) =
    40% × Resource Efficiency Score      (baseline audit + live usage vs. peer benchmark)
  + 30% × Recommendation Completion Rate  (verified recos ÷ total recos)
  + 20% × Guest Behavior Score            (% of guests opting in × avg savings achieved)
  + 10% × Accessibility Baseline Score    (self-audit checklist completion)
```

**Tag tiers:**
| Score | Tag |
|---|---|
| 0–40 | None / Getting Started |
| 41–70 | Bronze |
| 71–90 | Silver |
| 91–100 | Gold |

**Cold start:** New hotels receive a Baseline Score from the onboarding audit alone (can reach Bronze); the score becomes fully "live" once usage data and guest behavior data begin flowing in.

## 9. Data Model

**Supabase / Postgres** (durable/transactional data): `hotels`, `hotel_usage`, `recommendations`, `stays`. (Full schema — see Appendix A.)

**Upstash Redis** (ephemeral/fast-access data, replaces the earlier `route_cache` Postgres table): keys are namespaced and TTL'd per the caching tiers in Section 7, e.g.:
```
geocode:{normalized_place_text}              → { lat, lng, place_type, city, region, country }   (30-day TTL)
mode_feasibility:{fromGeoHash}:{toGeoHash}    → { viable_modes: [...], nearest_airports, nearest_stations } (7-day TTL)
route:{fromGeoHash}:{toGeoHash}:{mode}        → { distance_km, duration_hrs, cost, co2e_kg }       (24-hour TTL)
```
Note: the earlier static `routes` seed table is no longer required for the trip planner itself (all route data is resolved live), but a small seed set can still be kept for demo pre-warming and for populating the hotel discovery module's example listings.

---

## 10. Simulated Data Strategy

- **Hotel resource usage:** Generated via seed script — 90 days per hotel, weekday/weekend seasonality, 5% random-day anomaly injection (25–40% spike in one metric).
- **Hotel/route seed set:** 10–15 hand-crafted hotels and routes with realistic Indian travel context (e.g., Mumbai–Goa, Delhi–Manali).
- **Guest stays:** Simulated check-in/check-out records with plausible action-adoption rates for ROI Tracker demo data.
- **Not simulated:** transport carbon data (real, via Climatiq) and distances/routes (real, via Mapbox).

---

## 11. Non-Functional Requirements

- **Performance:** Trip search results returned within ~3s under cached conditions.
- **Reliability:** Demo must function fully offline-cache for pre-tested routes in case of live API failure.
- **Explainability:** Every score or recommendation shown to the user must have a visible "why" — no black-box numbers.
- **Accessibility (product itself):** Trip planner UI should support basic keyboard navigation and screen-reader labels, consistent with the platform's own theme.

## 13. Known Risks

| Risk | Mitigation |
|---|---|
| External API downtime/rate limits during live demo | Cache-first pattern, pre-warmed demo routes |
| Climatiq lacking India-specific emission factors | Verify factor availability in Phase 1; disclose as known limitation if unavailable |
| Gemini mode-feasibility reasoning is wrong/hallucinated for an unusual location pair (e.g., invents an airport that doesn't exist) | Validate any airport/station identifiers Gemini returns against a lightweight known-code check before calling Climatiq; if validation fails, drop that mode rather than pass bad data downstream |
| No rail-specific routing API — rail distance/feasibility relies on Gemini + Mapbox road-distance proxy | Disclose as a known approximation in the demo narrative; accurate enough for comparative ranking purposes |
| Judges questioning Green Score credibility | Formula and breakdown are visible/traceable, not just a number |
| Judges questioning loyalty program's business case | ROI Tracker shows transparent assumptions (participation rate, avg savings/redemption cost) |
| Scope creep given multi-day timeline | Phased build plan with MVP locked before stretch features |
